> Extension API: 1

## Model providers

- A model profile's context window now reaches Claude Code the same way whatever the model. A million-token window launches the model id with the `[1m]` suffix — the only lever that makes Claude Code use a million-token window and send the matching `context-1m-2025-08-07` beta — and any smaller window (128K, 200K, 256K, 512K) is declared, which used to happen only for a non-Claude model. Before this, a non-Claude model at 1M was launched with a bare id and a declared window, so the session compacted at an assumed 200K.

## Orchestrator

### The orchestrator agent and your questions

- With auto answer on, the orchestrator agent wakes when a task waits on a question it can answer, answers it from the task and repository context, and otherwise writes you one question with options in its chat. Questions only you can answer (budget, permissions, protected paths) still go to you directly.
- It tells you about each decision once. A reply reaches your chat only when a question it was woken for is still open; a turn that settled the question itself (a retry, a base check) is logged as done and says nothing. A question you already heard about is not repeated, also after a restart, until `waitRemindEveryHours` has passed. A notice is at most three lines: the decision, the options and a recommendation. A restart wake re-reads the waiting questions and decides silently.
- New `quietHours` setting (default `23:00-08:00` local time, `""` = off): in that window the agent starts no reminder and holds a notice for the morning digest, or, with `digestHour` off, for the first check after the window ends.
- The agent remembers how you answered. When a waiting question matches answers you gave before (the same kind of question, the same check commands and failure signals) and at least your two newest answers for it agree, it answers the same way without a notice or a turn, and the task records `Overseer: answered like owner precedent`. A lead's or its own earlier answer never counts.
- It never decides permissions, protected paths, budgets, accepting an attempt, dropping a check, security or sandbox changes, pushing or merging, paid services, deletions or production deploys — with or without a precedent — and an answer from it never counts as yours: it cannot accept an attempt that skipped review. Only you can drop a shared check (the repo's CI entry, a repo-settings check or one you wrote).
- The Improvements view has a DECISION MEMORY section. When you give the same answer twice, it shows a proposed rule you can Accept (it becomes a repo note) or Dismiss, and the 20 latest precedents with the check commands they are about, each with a Remove button.
- A question the agent is working on is held: no Inbox row, badge or notification until its turn ends without an answer (at most 10 minutes; a turn is stopped after 15). A wake it missed because its chat was busy runs when that turn ends; after a restart it is woken once per project with a waiting question it may answer.
- New `digestHour` setting: once a day at that local hour the agent writes a short digest in each active repository's chat — what finished, what waits on you, and today's spend.
- New `waitRemindEveryHours` and `waitDefaultAfterHours` settings: remind the agent every N hours about a waiting question, and after M hours answer a plan or agent question with its cautious option, recorded as an assumption you can overturn. Both are off by default.
- The agent opens a pull request when a task is done and green. It never merges, and it no longer has the `task_stop` tool.
- New Log view in the Orchestrator panel: what the agent did in the panel's project (woke, answered, opened a pull request, left you a note, digest, skipped, failed), newest first, with the project's spend today against the daily budget.
- Home shows the autonomy state: Autopilot, Auto-answer, the reminder interval, the default-answer delay and any active usage-limit pause with its local end time. Drafts from the Plan composer go into the NEXT backlog bucket, where the autopilot can start them, including when the planner is disabled.

### Planning and briefs

- Small task requests draft on the standard-tier route, with configurable character and path limits (`smallPlanMaxChars`, `smallPlanMaxPaths`; `0` disables it) and a recorded routing decision. Larger requests and lists use the planner.
- The planner drafts every part of a split task completely (title, goal, criteria, verify, finalVerify, paths, tier). A part with a title, goal, criteria and verify runs as drafted and skips its own planner; a part with an incomplete draft is still planned from its request.
- A dependent part drafted by the parent is refreshed once after the tasks it builds on landed, when they changed a file under its paths or one its check commands name: one cheap run on the brief-check route may correct its verify, finalVerify and paths. It never changes the goal or criteria, and a rewrite that removes a shared check is refused.
- When the brief check finds a contradiction in a planner draft, orchd resumes that planner's session once with a short correction turn instead of starting a new planner session. It drafts from scratch only when the session cannot be resumed or the reply is not a plan.
- When a planner puts a whole-repo suite (for example `npm run ci`, `cargo test --workspace`, or a package.json script that runs one) in `verify`, orchd moves it to `finalVerify`, where it runs once on the final tree, and records a decision line for each move.
- A backlog task created from a request stays `queued` and is planned only when it starts, on the head of its base branch as it is then.
- Every implement attempt that starts from the full brief gets a `## Where to look` block: the planner's paths, each file with the start of its text (at most 40 lines) and each directory with its entry names. Paths outside the worktree, missing and binary files are left out. A conflict-only attempt does not get it, and a resumed retry gets the shorter resume brief instead.
- The implementer runs only targeted tests (one test file or test name). The orchestrator runs the verification commands after the agent finishes and gives any failure back.
- New `implementBudgetMins` setting (default 45, 0 = off): an implement attempt still running at that time is stopped, its session is asked for a short report, and the attempt is recorded as `time_budget` ("out of time") with that report as its handoff for the next attempt.
- Retries after a failed check resume the implementer's session on the same route with the failure output and new owner answers. Rejected resumes fall back to a fresh run, and resumed Claude spending counts only the new attempt.
- Task runs receive their project's enabled MCP servers, with repo-specific `mcpEnable` and `mcpDisable` settings. Personal Claude servers and globally enabled connected tools are no longer added automatically; task messaging always remains available.

### Checks: faster, fewer and on the right tree

- orchd no longer waits for the base check before attempt 1: the checks run on the base in the background and hold no slot. Before landing, the task applies their result: a finalVerify that already fails on the base still asks, and nothing lands without its finalVerify passing on the final tree. A parent task still checks its base before its subtasks start, and its `finalVerify` base runs go to the background.
- The base checks start with the stored draft, beside the brief check, and start again when a redraft changes the commands.
- A task asks one base-check question listing every check that fails on the base, with drop-all and keep-all options. A failing check whose targets the plan creates is kept by rule. A check that fails on the base is rerun once alone; if it passes the second time the task goes on and records it as flaky.
- A "retry after the base is fixed" answer waits (no slot held) until the base branch has a new commit, carries the work onto it, then retries. Base-check results are kept on disk, keyed by base commit and command, so a daemon restart does not run them again; a run that timed out is never stored.
- Checks that already passed on the same worktree tree are reused across later gates. Checks that mention `ORCHD_BASE_SHA` run again when the base changes. Interrupted checks get one immediate rerun; timeouts and interrupted exits are never replayed from a cache.
- A whole-repo check a subtask shares with its parent runs once at the parent, on the final tree (`gateAt`, `"parent"` by default). Subtasks gated at their parent run package and matching Node tests for their changed files instead; unsafe or unmapped changes keep the full check.
- Repos can declare path-scoped shared checks in committed `.sushiai/setup.json`. They merge with the settings policy and are read at the task's base commit, so a task cannot edit them to skip its own checks.
- orchd limits check commands per machine separately from agent turns. The `heavyChecks` setting defaults to max(2, logical cores / 5); set a number to choose the limit, or `0` for none. A task waiting for a check slot records its wait. `parallel` and `heavyChecks` take effect without a restart.
- Check results record execution time and the load average and core count at their start. A timeout that started at a load at least the core count reruns once as an environment failure; a final check that ended only by timeout is rerun once on the same worktree with no new implement session.
- orchd shares one sccache compiler cache across task worktrees for setup, verification, base checks and final gates, while each worktree keeps its own build outputs; gate decisions report the cache hits. Set `compilerCache: false` in `.sushiai/setup.json` to opt out. Checks inside the task sandbox, and agents whose sandbox cannot reach the cache, run without it and record why.
- Desktop smoke reuses the build stamped by CI when tracked and untracked inputs are unchanged, and rebuilds after edits.

### Review and landing

- Reviews and slow final checks run together after the fast gates pass. A failed review cancels the checks. A failed check discards the review, and if that check also fails on the base and you drop it, the attempt is reviewed again before it can land: nothing lands without a review verdict.
- A review after a failed review is narrow: the open findings, the criteria not yet ruled met and the task's own changes since the reviewed tree. If the task changed a file since the last full review that no open finding names, orchd runs one full review before landing.
- Review `auto` never picks the route that did the work and prefers a route on another agent CLI.
- A landing carry that rewrites a file the review saw sends the same attempt back through verify and the review before it lands, also after the landing had to wait; a real conflict still gets exactly one more attempt on the newest base, with the files in its brief.
- A usage or rate limit no longer fails an attempt: the task pauses (5, 15, then 45 minutes, or until the stated reset time, at most six hours) and resumes by itself. Interrupted attempts and harness errors that changed no file no longer count toward `maxAttempts`. The loop detector counts failing tool results only when the same error repeats.

### Parallel work, graphs and visibility

- A file lease holds only the files a task has really changed, read from its worktree while it runs (also files a shell command wrote) and from `hook.edit`. Tasks whose plans overlap but whose edits do not run and land together. Planned paths still order sibling subtasks.
- A waiting task shows what it waits for: the free-text `queueReason` is replaced by a structured `wait` (`slot`, `subtaskSlot`, `dependency`, `file`), and the panel shows one label for each kind — or the open question, when there is one.
- Running graphs pick up base fixes outside their held paths before each part's next attempt; `orch.task.sync` merges on demand and returns conflicting parent files after aborting the merge.
- `orch.task.park` quietly pauses a task with a visible reason, releases its file leases, and resumes on `task.start` or when its optional `until` task finishes.
- Explicit stops clear open questions and release leases at once. A stopped task records who stopped it and why (`Owner: stop (UI)`), and `task.stop` takes an optional `reason`. Answers record their real source; after three retries of the same failure, the next failure parks for a fix without asking again.
- A task that ends `done` or `failed` gets `metrics`: first-pass, how often you were needed, spend per phase and, for a failed task, the cause (`env`, `plan`, `impl` or `review_loop`). A task report lists each implement attempt's exploration calls and time to first edit, and a `Total time` line.

### Pipeline view and presets

- A task's detail shows its pipeline as a diagram: Brief, Plan, Brief check, Base checks, Implement, Checks, Held-out check, Review, Judge and Land, with Advisor and the open question as a branch. The running stage is highlighted, a failed stage is marked, and each stage shows its model, time and cost.
- New Pipeline view in the Orchestrator rail: the repo's pipeline with a preset picker and an inspector that edits every stage's route, including the finding judge, shown as label and model.
- Three built-in presets: Fast, Careful and Docs. Editing a built-in preset makes an editable copy. A preset can be set per repo (`repoPresets`) and per task (`preset` on `task.create`, or `task.preset` before the first implement attempt). Shared checks stay owner-only under every preset.

### Task sandbox

- Task implement runs and all task checks share one filesystem policy. Native runs cannot read other known projects, other tasks' worktrees and daemon data, or Claude/Codex session archives (Codex may only see that its session date folders exist), and cannot connect to the daemon socket. Worktree Git metadata, build caches and temporary paths stay writable. Per-repo `sandboxRepos` overrides apply only to task runs.
- Codex implement runs use the same macOS Seatbelt profile as checks; their shell network stays open even with `codexNetwork=false`. Native checks disable Electron's nested renderer sandbox with `ELECTRON_DISABLE_SANDBOX=1` while keeping the task sandbox.
- Task tools and project secrets are isolated to the task's validated project. Full daemon MCP bridges are excluded from task configs, private per-run MCP files are cleaned up, and historical stored MCP values are redacted once.
- Sandboxed checks no longer execute the setuid process-list utility; native process inspection supplies process identity and CPU data.
- A test-launched sushiAI never touches your Keychain or your Desktop, Documents and Downloads folders.

### Worktrees

- Task worktrees live outside the repo, under `~/.sushiai/worktrees.noindex/<repo>/`, so Spotlight does not index them. The old `.sushiai/worktrees` setting counts as the new default; tasks that already exist keep their path.
- A repo can commit `.sushiai/setup.json` to prepare each new worktree (install dependencies); it runs once per worktree, also for base checks, and a failing setup fails the task with the output tail. Without it, a repo with a lockfile and no `node_modules` gets the matching install. orchd no longer links `node_modules` from the main checkout.
- `.worktreeinclude` lists ignored files to copy into each worktree. Without it, `.env`, `.env.local` and `.claude/settings.local.json` are copied as before.

## Projects

- A project can read its environment values on This Mac from HashiCorp Vault (KV v2, read-only). The project names a Vault address, a mount (`secret` by default) and one or more paths; the paths are merged in order, so a later path wins on a shared name, and a hand-entered variable with a saved value wins over Vault. The token is saved in **Settings → Vault**, encrypted with the macOS Keychain (safeStorage), and Vault values are kept in memory only, cached for five minutes, never written to disk or logged. If any path cannot be read (no token, no access, not found, unreachable, timed out), the project gets none of its Vault values and one notice says why; its hand-entered values still apply. SSH hosts never get Vault values. Known limit: new Vault values reach sessions and tasks at the next session start or the next orchestrator values push (`secrets.set`); an expiring cache does not push them by itself.
