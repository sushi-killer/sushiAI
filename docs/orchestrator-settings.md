# Orchestrator settings

Each host daemon stores its orchestrator settings in one settings object, read
and written as a whole (`settings.get` / `settings.set`). In **Settings →
Orchestration**, Host scope edits that object directly; a key with no control
there is edited under **Advanced — all settings as JSON**. Project scope layers
project defaults and host overrides over those daemon settings; see below. The
source of truth for the settings object is the `Settings` struct in
`crates/sushiai-orch/src/policy/settings.rs`; the defaults below are the ones a fresh
install gets.

Settings hold no secrets. Model-provider keys stay in **Settings → Models**.

## The Orchestration tab and hosts

The **Host / Project** choice selects which scope the tab edits. In Host scope,
the **Settings host** select chooses the host daemon and appears only when more
than one host is registered. The tab edits one host at a time. It also offers
**Copy settings to…** when another host is available: this copies the selected
host's saved settings read from its daemon, not unsaved edits in the tab. It
replaces the target host's settings while keeping that host's host-specific
keys listed below.

In Project scope, choose a project and either **No host (project default)** or
one of that project's hosts. Editing the project default sets values used by
every host in the project. Editing a host sets per-host overrides on top of
that default. The host view shows the effective settings: host daemon settings,
then project defaults, then that host's overrides. `inherited from project`
marks a value supplied by the project default. `overridden on <host> ↺` is a
control that removes that host's override; Save writes the reset. In the
project-default view, `project default ↺` removes that default; Save writes
the removal. Save stores the project layers and writes each host's effective
settings through that host's daemon.

### Host-specific keys

These keys refer to paths or repos on a particular host's machine (some
values also carry commands tied to those repos). **Copy settings to…** keeps
the target host's values for these keys and does not carry the source values
over. Project scope treats these keys like other settings: it applies project
defaults over each host daemon's settings, then that host's override on top.
Use a per-host override when a value needs to differ by host.

`worktreeRoot`, `sandboxRepos`, `landOnDefaultRepos`, `gateAt`, `afterLand`,
`scopedChecks`, `mcpEnable`, `mcpDisable` and `repoPresets`.

## Task sandbox

Task implement runs and their setup, base, verify, held-out, screenshot, eval and final checks use the repo's `sandboxRepos` entry, falling back to `sandbox`. Chat, overseer, pane agents and plan/review/brief-check/advisor/judge stages keep their existing global settings and daemon-data read deny. Saved global sandbox values are never migrated.

Native task reads are open except for other known project folders, other task worktrees, daemon data and `~/.claude/projects`, `~/.codex/sessions`, and `~/.codex/archived_sessions`. Known folders come from project mappings and stored tasks' repos. The default `<SUSHIAI_HOME>/worktrees.noindex` root and configured `worktreeRoot` are denied, with only the current worktree re-allowed. Relative roots are resolved for every known repo; stored tasks' actual worktree paths remain denied after the setting changes. For a registered ancestor of this repo, its other children are denied when the policy is built. Checks and Codex can read their own run directory and worktree inside denied storage roots. Seatbelt permits only metadata access to their ancestor directories so builds can resolve their paths; other directory contents remain denied. The installed Claude schema supports `sandbox.filesystem.allowRead`, so its shell gets those same exceptions. Claude's Read-tool denies cannot be overridden by `allowRead`: when a denied root contains the current worktree, the policy denies its other children recursively instead, preserving Read, Grep, Glob and Edit in the worktree. Daemon data, including the run directory and its credentials, stays denied to the Read tool; if the worktree itself is under daemon data, only that worktree is excluded. Native Claude implements load only orchd-supplied settings, so project/local sandbox grants and hooks cannot widen the policy; project instructions and explicitly scoped MCP definitions still load. Claude starts its MCP servers and orchd hooks outside its shell sandbox, preserving their bridge.

Writes are allowed under the worktree, Git common directory and worktree metadata, own run directory, `TMPDIR`, `/private/var/folders`, `/private/tmp`, `/dev`, cargo/rustup homes (`CARGO_HOME` / `RUSTUP_HOME` or their HOME defaults), npm cache (`npm_config_cache` / `NPM_CONFIG_CACHE` or `~/.npm`), `~/.cache`, `~/Library/Caches`, and `~/.codex`. A worktree's symlinked `node_modules` target is writable only when it points to this repo's main checkout dependencies. Codex session reads remain denied despite its writable state directory, except for metadata-only access under `~/.codex/sessions` (owner decision 2026-10-12) so Codex can check its date directory before writing a session file; session contents and listings remain denied.

Checks and Codex task implement runs use `sandbox-exec` on macOS. That wrapper is unavailable on other systems. Codex implements, including resume, use `--sandbox danger-full-access` with the outer task profile; reviews keep `--sandbox read-only`. The specific token-less daemon socket is denied, so native Codex implement runs omit the messaging bridge and have no peer messaging or `ask_orchestrator`. A per-repo host entry restores the bridge. Incoming messages can still reach the next attempt brief. Token-checking the socket is a separate follow-up.

Native task runs and checks receive `RUSTC_WRAPPER=""` and have inherited `SCCACHE_*` variables removed, so Cargo does not start sccache inside the profile. Native checks also receive `ELECTRON_DISABLE_SANDBOX=1`. This disables Electron's own renderer sandbox inside the outer sandbox; the task filesystem and socket restrictions still apply. Host checks receive neither policy-added environment change. Checks keep open network. Codex task shell commands also have open network even with `codexNetwork=false`, because its workspace-network switch does not restrict `danger-full-access`. Claude retains its `allowedDomains` filter.

The same-failure retry cap is fixed at **3**, with no setting: after three
retry answers from any source for the same failure signature, the next same
failure parks the task with a visible reason and asks no question. Fix the
cause, then use `task.start` to resume it.

The Orchestrator panel's Log view lists what the orchestrator agent did in that panel's project when `autoAnswer` or `digestHour` woke it (`<data>/overseer.jsonl`, last 2000 entries), with this project's spend today (UTC day) and, when `dailyBudgetUsd` is set, the total of all projects against it.

Decision memory. Every answer to a task question (yours, a lead's, the overseer's, the chat's, a rule's, the waiting default's, a judge's) adds or merges one precedent in `<data>/precedents.json` (mode 0600, up to 200 per repo, newest kept): the question kind, the check commands, signals read from the check results (`timeout`, `install`, `flaky`, `outside_diff`), the changed files, the goal, the answer, who gave it, a one-line why and a count. A check's output is never stored. With `autoAnswer` on, a waiting question that matches your own earlier answer (same kind, failure signature, signals and commands, or for a free question the same text and options), where your newest answers for it agree and the answer is still one of its options, is answered by the overseer with no turn and no notice. The task records `Overseer: answered like <owner precedent: answer, YYYY-MM-DD> -- <question> -> <answer>`, and the overseer log gets an `answered` entry. Lead, overseer, policy and judge precedents never answer, and neither does a stored `stop`. These always go to you: permission, protected path and budget questions, accepting an attempt, dropping a check or criterion, anything about the sandbox or security, pushing, pull requests, merging and releases, paid services, deleting and production deploys. Every other guard of `task.answer` still applies (the continue cap, one non-owner base retry per base, shared checks); a refusal wakes the overseer as usual. The overseer's own `task.answer` takes an optional `like` (at most 120 characters) with the same limits. An overseer wake carries up to five of your matching precedents. When you give the same answer twice for one question, the Improvements view shows one proposed rule under DECISION MEMORY: Accept makes it a repo note, Dismiss stops it being proposed again; nothing adopts it on its own, and the overseer never writes a repo note (the daemon refuses `repo.notes.add` and `repo.notes.remove` from it). The view lists the newest 20 precedents, each with a Remove button. `precedents.list`, `precedents.remove`, `precedents.rule.accept` and `precedents.rule.dismiss` take `{repo}` (and `id`) and are not MCP tools.

A question the orchestrator agent is looking at (its turn has started or is queued) is held: it carries `heldForOverseer: true` and `heldAt`. The app raises an Inbox row, Dock badge, count or notification for a waiting task only when its question carries `forOwner: true`, which the daemon sets once nobody else will settle it: at once for questions only you may answer (also in quiet hours), with `autoAnswer` off, when no overseer turn can start (no route, no repo directory), and at daemon start for questions nobody will take; otherwise when the overseer's turn ends with the question still open, including a turn that outlives its hold. A turn is cancelled after 15 minutes (logged as failed, "timed out"); a hold older than 10 minutes ends, and the question is yours when that turn ends. When quiet hours hold the overseer's notice, the question is yours once they end, with the digest on or off. Once set, `forOwner` stays until the question is answered or replaced; a later reminder or restart turn does not take it back. A question the answer policy or one of your precedents answers never gets it, and neither does "attempts keep failing": the failure ladder settles that one. Questions only you may answer are never held.

A base check that fails on the task's base commit is run once more alone (the pair of runs is the only base-check pair of its repo at that time). If the rerun passes, the task records `Orchestrator: base check <cmd> flaky on <sha>: passed on rerun` and goes on without a question. A background final base check publishes this decision when it finishes, even if the task has already finished; passing final checks do not wait for it. The checks that fail twice are asked about in one question per task that lists every one of them (`commands`), with the options "keep all" / "drop all" / "stop" for a parent and "retry after the base is fixed" / "drop all" / "stop" for a single task. A failing check is kept by rule, with no question, no overseer wake and no feasibility judge run, when at least one file, directory or glob it names is absent on the base commit and the task has subtasks or the name lies under the paths of the task or of a subtask: the plan creates it, and the task records `Orchestrator: kept check <cmd>, targets absent on base; the plan creates them`. Only you may answer "drop all" when any listed check is shared (nothing is removed then): the repo's CI entry (`npm run ci`, `npm test`, `cargo test`), a `scopedChecks` or `afterLand` command, or a command you wrote in the task request. The orchestrator agent, the answer policy and the waiting default can answer "retry after the base is fixed" or "stop" for those; a check the planner invented for one task can still be dropped by the agent.

Checks that exit 0 are reused across later gates on the same Git worktree tree. A pass is cached only when the tree is unchanged after the command: a check that changes tracked or untracked files must run again, including after a base preflight. Ignored build outputs do not change the tree. The cache key is the tree id and exact command text; the base sha is included only when that text contains `ORCHD_BASE_SHA`, since a check can read it. The cache holds at most 512 entries in insertion order, evicting the oldest, and lives only in memory until the daemon stops. A reused check records `Orchestrator: <cmd> already passed on tree <short id>; not run again` and counts as a pass without running. Held-out decision lines use `held-out check (criterion N)` in place of the command.

An interrupted check runs once more at once unless cancelled. The same runner retains check-slot admission and the machine-load diagnostics: a timeout under load is classified as an environment failure even if its rerun exits non-zero. Interrupted means no exit code (except cancellation, spawn failure or an internal runner error), exit 124, 137 or 143, or a line containing `timed out` or `timeout` (case-insensitive) in the `--- failures ---` section of its tail. The task records both run durations in seconds and the rerun result: `Orchestrator: <cmd> was interrupted after ... s (...); ran it again at once: ... after ... s`. Interrupted outcomes are never cached as failures in either the base or verify result cache, so a later retry runs afresh. A still-interrupted base run is not treated as an existing base failure; a grounded baseline check that is still interrupted remains a failing baseline.

Review runs alongside the final checks after fast verify, grounded checks, evidence and protected-path approval; a failed final check discards the review, and a failed review cancels the checks.

A retry after a failed check or an implement time budget resumes the previous implement session when its route, harness and model are unchanged. The brief gives the current criteria, checks and verification commands, with previous failure output kept as history and new owner answers. A time-budget retry asks to continue the work; it does not claim a check failed. Route changes or best-of attempts, repeated review findings and loop-stopped runs start fresh, and a rejected resume falls back to a fresh run in the same attempt. No separate report turn runs after a timeout. Tool failures are for the harness to diagnose; exact repeated calls and edits, the stall watchdog, budgets, cancellation and attempt limits remain enforced.

## Worktree environment

A new task worktree is a clean checkout: it has no installed dependencies and no ignored local files. orchd prepares it before the first attempt, before a base check and before an eval check.

**`.sushiai/setup.json`.** A repo commits this file to say how to prepare a worktree:

```json
{
  "setup": "npm ci",
  "env": { "NAME": "value" },
  "compilerCache": true,
  "format": "./node_modules/.bin/prettier --write --ignore-unknown \"$@\"",
  "scopedChecks": [
    {
      "command": "npm run test:desktop",
      "paths": ["electron/**", "src/app/**"]
    }
  ]
}
```

`setup` is a string (run with `sh -c`) or an argv list (run directly). `env` is optional. The command runs once per worktree, in the worktree, in the same sandbox as the checks (`Host` runs it unsandboxed, as it does a check), with the verify timeout. On macOS it gets `npm_config_cache` under `~/Library/Caches/sushiai/npm`, a path the sandbox lets it write. It gets orchd's own environment plus the extended `PATH`, `ORCHD_ROOT_PATH` (the main checkout), `ORCHD_WORKTREE_PATH` (the worktree) and the `env` of the file. No project secret is added. If `setup.json` is not valid JSON, or the command exits non-zero, the task ends `failed` with no attempt and a decision line `Worktree setup: ...` that holds the tail of the output. Stopping the task stops the setup. A worktree recreated from its branch runs the setup again.

`format` is optional and has the same shape as `setup` (a string run with `sh -c`, or an argv list). After orchd writes the planner's test files and before it commits them, it runs the command in the worktree, in the same sandbox and environment as setup, with the repo-relative test paths as arguments (`"$@"` in a string, appended to an argv). The committed file, its protected hash and the stored task test all hold the formatted text, so the repo's own format check passes on files the task may not edit. Like the check declarations, it is read from the task's base commit. If the command fails or runs longer than 120 seconds, the tests are committed as written and the task records `Orchestrator: format command failed on planner tests (...), committed as written`.

`scopedChecks` is an optional list of `{command, paths}` entries. Unknown keys
in the file or an entry are rejected. The command is a glob over the complete
check command; paths are globs over repo-relative files. Unlike setup and env,
check declarations are read from `.sushiai/setup.json` at the task's base
commit, never from its edited worktree. They are merged with
`settings.scopedChecks` and apply only to this repo. The same path filter is
used by verification, the Stop hook and best-of evaluation; the base preflight
uses the task's planned paths, and the planner brief lists the merged policy.
Repo-declared checks are shared checks: only the owner may drop one. Adding or
editing a declaration during a task cannot skip that task's own check.

**Scoped subtask checks.** After path scoping, a subtask in a repo with
`gateAt: "parent"` replaces each broad CI-entry command with checks for its
changed files. Files inside a crate use `cargo test -p <package name>` from the
nearest ancestor `Cargo.toml` with `[package]`. Changed `*.test.cjs`,
`*.test.mjs` and `*.test.js` files use `node --test <file>`; source files also
use existing tests with the same stem before `.test.`, in the source's own
directory or anywhere under the root `tests/` directory. Derived commands are
deduplicated and retain tree-pass reuse and compiler-cache reporting. Commands
already naming `-p`, `--package`, `--test`, `--manifest-path` or a file, and
commands that are not CI entries, run unchanged. With `gateAt: "every"`,
subtask scoping is disabled.

Any unmapped changed file keeps the full command. The unsafe files always do
so: the root `Cargo.toml`, any `Cargo.toml` with `[workspace]` or without `[package]`, `Cargo.lock`, any
`package.json`, `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`,
`.sushiai/setup.json`, `rust-toolchain*`, `.cargo/config*`, `tsconfig*.json`,
`vite.config.*`, `eslint.config.*`, `.prettierrc*`, `Makefile` and `.github/**`.
The original scoped command remains a parent check. If absent from the
parent's trimmed `verify` and `finalVerify`, it is added to `finalVerify`.
The parent still runs `verify` plus `finalVerify` on the combined tree; a
parent that is itself a subtask can scope to its own parent. Decisions record:

- `Orchestrator: subtask ran <derived joined by "; " or "nothing"> instead of <cmd>; the parent runs <cmd> on the combined tree`
- `Orchestrator: subtask runs <cmd> in full: <file> maps to no package or test`
- `Orchestrator: added <cmd> to finalVerify for subtask <short id>`

**Default install.** A repo without `setup.json` gets `npm ci`, `pnpm install --frozen-lockfile` or `yarn install --frozen-lockfile` when it has `package-lock.json`, `pnpm-lock.yaml` or `yarn.lock` and no `node_modules`. A `setup.json` replaces it. orchd no longer links the main checkout's `node_modules` into a worktree.

**`.worktreeinclude`.** A file in the main checkout, in gitignore syntax, lists ignored files to copy into each worktree (for example `.env*`). Only regular files that the main checkout ignores and git does not track are copied; a symlink is skipped and a file the worktree already has is kept. Without this file, `.env`, `.env.local` and `.claude/settings.local.json` are copied when ignored.

**Compiler cache.** `compilerCache` is an optional boolean in `.sushiai/setup.json`, on by default. Setting `"compilerCache": false` disables orchd's compiler wrapper, server startup and cache decision lines for that worktree, including a file with no `setup` step. When `sccache` is on the extended `PATH` and the owner has not set `RUSTC_WRAPPER`, setup and every verify command (including base checks, final checks and the parent gate) get:

```text
RUSTC_WRAPPER=sccache
SCCACHE_DIR=$HOME/.cache/sushiai/sccache
SCCACHE_SERVER_PORT=4227
```

Port 4227 and the cache directory are dedicated to orchd, shared across its task worktrees, separate from sccache's defaults. The daemon runs `sccache --start-server` with this environment outside any sandbox and any check's process group, so stopping a check does not stop the server. orchd never sets `CARGO_TARGET_DIR`: every worktree keeps its own `target/` outputs. Without sccache, or when the owner supplies a wrapper, orchd leaves the compiler environment unchanged and writes no cache line.

Agents get the same compiler environment when their sandbox can reach localhost and write the cache directory. A Codex agent with `codexNetwork: false` gets no injected wrapper, and the task records `Orchestrator: compiler cache disabled for agent: Codex codexNetwork false blocks localhost access` once. A read-only Codex agent, or an agent whose sandbox only permits writes in the worktree, also skips the wrapper with a reason line. orchd does not expand the agent's sandbox permissions for caching. Host-mode Claude agents can use the shared cache; Codex keeps its workspace sandbox even in Host mode.

After a verify run, final checks or the parent gate, orchd reads its server's JSON stats before and after the run and records one line from the difference, for example `Orchestrator: compiler cache 41/52 hits (79%) in final checks`. It writes no hit-rate line when there were no compile requests or stats could not be read; reused verify results do not produce another line. These are counters from the shared server, so concurrent builds can contribute to the same interval. sccache caches eligible compilations, not Rust's incremental builds or linking; each repository controls its Cargo profiles. Rust cache keys also include a crate's working directory, so registry dependencies at stable paths can hit across fresh worktrees while copies of a worktree's own crate can still miss.

## Presets

A preset is a named set of pipeline choices that a task can start from. The
Pipeline view in the Orchestrator rail draws the pipeline and holds the preset
picker; a task's detail shows the same diagram for that task.

Three built-in presets are defined in code (`Preset::builtins` in
`crates/sushiai-orch/src/policy/presets.rs`). They are read-only and are always listed
before the custom ones.

| Preset              | Brief check | Advisor | Held-out check | `maxAttempts` |
| ------------------- | ----------- | ------- | -------------- | ------------- |
| Fast (`fast`)       | off         | off     | off            | 2             |
| Careful (`careful`) | on          | on      | on             | 4             |
| Docs (`docs`)       | on          | off     | off            | 2             |

A preset sets only the values it names. The values a preset can carry:

| Value             | What it sets                                                                    |
| ----------------- | ------------------------------------------------------------------------------- |
| `briefCheck`      | `false` turns the brief check off; `true` uses the settings' `briefCheckRoute`. |
| `advisor`         | The advisor after a failed attempt.                                             |
| `heldOut`         | The held-out check (`experiments.heldOut`, on by default).                      |
| `planner`         | The route for the planning stage.                                               |
| `briefCheckRoute` | A route id for the brief check; wins over `briefCheck`.                         |
| `review`          | The review route: a route id, `"auto"` or `""`.                                 |
| `tierRoutes`      | Route ids per tier (`mechanical`, `standard`, `hard`).                          |
| `maxAttempts`     | Attempts before the task fails; at least 1.                                     |

`presets` (custom presets) and `repoPresets` (`{repoPath: presetId}`) are
saved through `settings.set`, which refuses a preset whose route is not
configured, a duplicate or built-in id, `maxAttempts` of 0, and a
`repoPresets` entry that names an unknown preset.

- **Per task.** `task.create` takes an optional `preset`; without it the task
  uses its repo's preset from `repoPresets`. The preset is written into the
  task's variant, so a later settings change does not move a task that has
  been created.
- **Changing it.** `task.preset {id, preset}` sets a task's preset, but only
  before its first implement attempt. After that it is refused, and so it is
  while the task's loop is live.
- **Editing in the Pipeline view.** A built-in preset is read-only: an edit
  in the inspector makes an editable custom copy and selects it for the repo.
  Edits to the repo's own custom preset are saved in place.
- **Shared checks.** Shared checks (the repo's CI entry and base checks) are
  owner-only. No preset and no inspector switch disables them.

## How a task is planned, gated and reviewed

- **Plan gate and one replan.** After the planner's draft is stored and
  before any question or split, one read-only review of the draft always runs.
  It uses `planReview` when that route is configured and available, otherwise
  the planner's route; a `Plan gate:` decision line says which. The review
  returns typed findings (missing requirement, report-only, untestable, wrong
  split, wrong approach; severity critical, high or medium). A reply that does
  not match that schema counts as no usable review, and the gate continues. A
  typed report-only finding removes the criterion it names. Any other critical
  finding runs the planner again once, with the findings in the prompt; the
  request text is never edited. Findings left after that reach the implementer
  as plan notes.
- **Merged checklist tasks.** Subtasks that list no paths, have no check or
  overlap another part are merged into one task with a checklist, in planner
  order. Each item's check runs before the full verify of every attempt and a
  failing item fails the attempt by name. If one task remains it is the parent
  itself.
- **`groundedChecks` is removed.** The flag is no longer read. A settings
  file or task that still carries it loads, and the key is dropped on the next
  save. Checks are always baselined on the base commit.
- **Protected planner tests and the held-out check.** The planner's test
  files are committed first, hashed and denied to the implementer; an attempt
  that changes them has them restored. The planner's checks and one held-out
  check run on that commit before attempt 1: a check that already passes
  proves nothing, one that cannot run is an environment fault, one that
  fails gates the task. The held-out check is hidden from the implementer, its
  failure has kind `heldout`, and its command appears in no brief or detail.
- **Two review rounds, stable finding ids.** A review runs at most twice per
  attempt (once more only after a missing verdict or a judge's drop). Every
  finding has a stable id (`F-...`) that follows it across attempts, so a
  finding that returns is recognised, and one that repeats twice goes to a
  check or to the judge. After round two the last result stands and the owner
  gets no further retry.
- **Overseer state files.** Every overseer wake runs on a fresh harness
  session and never touches the owner's session id. Per repo, orchd keeps one
  file `<data>/overseer/<hash of repo>.md` (mode 0600) with the repo's open
  tasks, the plan of the wake's task and the last 50 decisions. It is
  rewritten when a wake starts, put at the top of the wake prompt, and gets one
  decision line per wake. Check output is never written to it.
- **Metrics in the `done` entry.** When a task ends `done` or `failed`, orchd
  stores `metrics` on it and a top-level task adds one `done` entry to the
  overseer log. Its text is
  `first pass: yes|no; owner touches: N; cause: none|env|plan|impl|review_loop; cost: plan $0.02, implement $0.01`
  (only nonzero phases, in the order plan, implement, review, triage,
  advisor, finding_judge, answer_judge, pick; `cost: $0.00` with no spend).
  First pass means done with exactly one implement attempt, that attempt
  passed, and no review or registered finding other than P3 (a finding with no
  severity counts as blocking). A parent is first pass when it ran no
  implement attempt of its own and every subtask is first pass by the same
  rule, at every depth. Owner answers do not change it. Owner touches count owner-answered questions plus
  `Amended: ` decision lines. The cause comes from the last failure: errors,
  cost budget, a missing harness and base-check failures are `env`; a failed plan
  stage or a plan-gate drop is `plan`; verify, held-out, loop, stall,
  protected path, implement time budget, no deliverable, evidence, conflict and blocked are `impl`;
  review failures, the review-round limit and repeated findings are
  `review_loop`. The entry detail adds the repo's first-pass rate and the
  average cost per landed task over its last 20 finished top-level tasks.
- **Late planning.** A task created with a `request` and a backlog bucket is
  saved `queued` and plans nothing. When `task.start` or the autopilot starts
  it, its worktree first moves to the current head of its base branch (when no
  attempt ran and nothing in it changed), a `Rebase: planning from` decision
  line is recorded when the head moved, and the plan is drafted on that code.

## `experiments` flags

| Flag                                                  | Default | What it does                                                                                         |
| ----------------------------------------------------- | ------- | ---------------------------------------------------------------------------------------------------- |
| `stallTimeoutSecs`                                    | `0`     | Stop an attempt whose harness prints nothing for this long; 0 is off.                                |
| `reviewEvidence`                                      | `false` | The reviewer gets saved screenshots and longer verify output.                                        |
| `heldOut`                                             | `true`  | Run the hidden planner check. Regular behaviour checks always run.                                   |
| `advisor`                                             | `false` | After a failed attempt, one read-only call diagnoses it for the next attempt.                        |
| `loopDetect`                                          | `true`  | Stop an attempt that repeats itself.                                                                 |
| `land`                                                | `true`  | A passed task lands on its base branch by itself (never on the default branch unless allowed above). |
| `maxCostUsd`, `maxAttemptCostUsd`                     | `0`     | Dollar caps per task and per attempt; 0 is none.                                                     |
| `batchQuestions`                                      | `true`  | A planner question that is not blocking and has a recommendation becomes an assumption.              |
| `plannerRoute`, `tierRoutes`, `bestOf`, `bestOfRoute` | off     | Experiment arms; see `Variant` in `crates/sushiai-orch/src/policy/variant.rs` for each.              |

Only settings reachable through the app are listed with a control. A key
missing from the list above but present in `crates/sushiai-orch/src/policy/settings.rs` is still
editable in the Advanced JSON, which shows the whole object as the daemon
returned it.
