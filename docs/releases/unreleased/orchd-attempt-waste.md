## Orchestrator

- The implementer runs only targeted tests (one test file or test name). The orchestrator runs the verification commands after the agent finishes and gives any failure back, so the agent no longer runs them or a whole-repo suite itself.
- New `implementBudgetMins` setting (JSON settings editor, default 45, 0 = off): an implement attempt still running at that time is stopped, its session is asked for a short report, and the attempt is recorded as `time_budget` ("out of time") with that report as its handoff for the next attempt.
- When the brief check finds a contradiction in a planner draft, orchd resumes that planner's session once with a short correction turn instead of starting a new planner session that reads the repo again. It drafts from scratch only when the session cannot be resumed or the reply is not a plan.
- orchd no longer waits for the base check before attempt 1. Attempt 1 starts at once; the checks run on the base in the background and hold no slot. Before landing, the task waits for that check and applies its result: a finalVerify that already fails on the base still asks the owner, and nothing lands without its finalVerify passing on the final tree. A parent task still checks its base before its subtasks start.
- When a planner puts a whole-repo suite (for example `npm run ci`, `cargo test --workspace`, or a package.json script that runs one) in `verify`, orchd moves it to `finalVerify`, where it runs once on the final tree, and records a decision line for each move.
- A review after a failed review is narrow: the reviewer gets only the open findings of that review, the criteria it did not rule met (the others are listed as settled) and the task's own changes since the reviewed tree, not the full diff. If the narrow review passes but the task changed a file since the last full review that no open finding names, orchd runs one full review before landing and its verdict stands.
- A "retry after the base is fixed" answer no longer starts an attempt on a base that has not moved: the task waits (no slot held) until the base branch has a new commit, carries its work onto it, then retries. Base-check results are kept on disk, keyed by base commit and command, so a daemon restart does not run them again; a run that timed out is never stored. A final check that ended only by timeout is rerun once on the same worktree as an environment failure, with no new implement session.
