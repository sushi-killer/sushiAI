## A red base no longer stops a task

- A final check that fails on the task's branch and also on its base is judged by the failing tests, not by its exit code. orchd reads the whole output of the check (cargo test and nextest, node TAP, pytest, jest and vitest, go test, or any line ending in `FAILED`). A task that fails no test the base does not fail passes, and its decisions say `base failures on <sha> accepted: <tests>`; the shared check stays in the task. A task that adds a failing test gets an ordinary failure to fix. New failures are re-run once: failures that change between runs count as the base's. orchd asks the owner only when neither output names a test, the outputs differ and the check printed something.
- "Retry after the base is fixed" waits at most 2 hours. While it waits, the task shows why and holds no slot and no file claim. Only a task that is running or landing counts as one that can move the base, so two red tasks no longer wait on each other. After the wait the question comes back instead of another wait.
- A task that hit the "failed again after 3 retries" or "conflict attempt failed" rule is no longer parked silently. It pauses 30 minutes, tries again, and after two retries it fails with its reason in the decisions.
