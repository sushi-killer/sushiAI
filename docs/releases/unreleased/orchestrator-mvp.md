## Orchestrator: tasks carried to a verified done

- A new panel type, **Orchestrator**, turns a goal into a task that agents carry to done without you watching. You describe what you want to the orchestrator in the panel's chat; it checks the request is clear, asks you when it is not, and files the task. A planner session drafts the goal, the acceptance criteria and the commands that prove it, asking any open questions one at a time. sushiAI then creates a branch `task/<name>` and a worktree next to the repository and runs fresh Claude Code or Codex sessions in it until the checks pass.
- The orchestrator only reads your project and manages tasks - it never edits files itself. The conversation runs in the background service too, so a reply keeps coming and the chat is still there after you close or restart sushiAI. Any agent can take that role by attaching `orchd mcp` as an MCP server.
- "Done" is decided by the app, not by the agent: the changed files come from git, the verification commands must exit 0, and an independent read-only review by the other vendor's model has to pass. A passing attempt is committed on the task branch with `Task-Id:` and `Attempt:` trailers. Nothing is pushed.
- When an agent says it is finished while a check still fails, a stop hook sends it back with the failing output, at most three times per session.
- A failed attempt starts a fresh session with the failure in its brief; the same failure twice moves the task to a stronger model, three times (or running out of attempts) asks you one question with options. Answering continues the task; answering "stop" ends it. A waiting task raises a notification.
- Task agents can see the other tasks in their repository, message each other and ask the orchestrator a question without stopping their work. A message never interrupts a running attempt: it arrives with the recipient's next attempt, and a question wakes the orchestrator in the same conversation you chat with, whose answer goes back to the task. The panel's **Messages** section shows every thread and whether each message has arrived yet.
- Agent sessions run in the macOS sandbox by default, with only the project's own MCP servers plus the messaging tools above, and no personal plugins, hooks or skills. Verification commands run sandboxed too.
- Tasks run in a separate background service, so they keep going when the window closes or sushiAI quits, and the panel shows their live state when it opens again. If that service itself is stopped mid-task, the task picks up again with a fresh attempt when it restarts.
- Every automated decision is listed in the task: the tier a task runs on and, when you turn on "Answer stuck questions for me", the orchestrator answering a stuck agent's question for you ("Orchestrator"). It never approves protected paths, stops a task or grants more attempts on your behalf.
- Settings → Orchestration sets the routes (Claude or Codex, model, effort, or a custom Claude model from Providers), which route handles simple, standard and hard tasks, the reviewer, the planner, the orchestrator's own model, the sandbox and its allowed domains, Codex network access, attempts, parallel tasks and paths that need your approval.
