## Architecture diagrams in Preview

- A JSON Canvas file (`.canvas`) opens in Preview as one diagram. Every part is a block with a shape (box, pill, diamond, cylinder, person or circle), an icon, a caption and an optional step number. Use it for an architecture, an order of steps of an agent or a skill, or a change as-is / to-be: each part gets a delta (new, changed, exists or removed), and the marks on the board show the change.
- The agent draws and changes the diagram from the terminal. You build it too: right-click the board (or use the + button on it) to add a component, boundary or note where you clicked; drag, connect, rename and delete parts; move and resize boundaries and drop components into them; edit everything in Inspect.
- Drag on an empty spot of the board to select several parts at once (hold Shift to add more, Cmd or Ctrl+A for all), then move them together with the mouse or the arrow keys, change what they share in Inspect, or delete them. Pan with two fingers, Space and drag, or the middle button.
- Accept or reject parts the agent proposed, and comment a selection to send it to the agent.
- Edits from both sides merge into the same file. The agent gets one note to reread the file after your edits, not one per edit.
- The file is plain JSON Canvas, so it also opens in Obsidian and other JSON Canvas tools. The new, changed and removed marks are colours there too (4, 3 and 1). Shapes, icons, step badges and the proposed state live in a `sushiai` field that other tools may drop when they save.

## Extension icons

- Extensions can declare one default `icon`, and built-in Settings tabs (Vault, Orchestration, Routines) and extension cards now show their own distinct icons instead of the same plug.
- Eight more bundled icons are available to extensions, and every icon now draws with the same stroke width and size.

## Orchestrator tasks start after an owner answer

- A task no longer stays queued after the owner answers a question. A check decision written while the first attempt started could overwrite the attempt, and the task then never ran on.

## Orchestrator compiler cache hits across worktrees again

- When a host cargo setup points every checkout at one shared target directory, orchd gives each task worktree its own target. The compiler cache now still hits across those worktrees; before, every worktree compiled from scratch.

## Orchestrator keeps new cases in a test file a check names

- An agent may now add new lines, such as new test cases, to an existing test file that a task's checks name; before, orchd put the file back and the task burned its attempts. A changed or removed line is still put back, and the planner's own test files stay unchangeable. The review is shown the added lines and asked to confirm they do not weaken a test.

## Orchestrator plans only checks the repository defines

- The planner proposes only scripts the repository defines today.
- When the repository's CI script already picks the checks a change needs, the planner uses it as the final check and adds no whole suites it would skip.

Orchestrator tasks no longer stall on their own checks: a file a check expects to change or disappear stays editable, a re-plan may replace a check its own plan wrote, and checks for files a task adds see those files before they are committed. A scheduled routine whose agent answers within moments keeps its answer.

## Pull request checks are watched

- After orchd opens a pull request it watches the pull request's GitHub checks until they finish.
- A red check that is the task's own goes back to the task's agent for one repair step with the failed job log, and the fix is pushed to the same pull request.
- A red check that is not the task's (it passes on a rerun of the failed jobs, or the base branch fails the same test) leaves the task alone, and the owner gets one note naming the test and why.

## Routine results keep their last lines

- A routine run's result keeps the output its agent printed just before it exited. The end of the output was lost when the session's exit reached the routine before its last output.

## Sessions already running on a host

- Sessions a connected host already runs but no panel in this app shows (started on another machine against the same SSH host, or by the `sushiai` CLI) now appear in the sidebar and the Inbox. Click one to attach to it with its current screen.

## Skills have one owner

- The `sushiai` binary now owns every skill folder: `sushiai skills --json --catalog` is the Skills screen's catalog, and `sushiai skills install|remove NAME` installs and removes the skills sushiAI ships (`sushiai-artifacts`, `sushiai-routines`, `sushiai-orchestrator`). The app runs the binary instead of writing folders itself.
- A builtin skill is installed once per harness: into Claude Code's folder and into Codex's `$CODEX_HOME/skills` only. An older copy of ours in `~/.agents/skills` is removed, so Codex no longer loads it twice.
- Nothing is installed for a tool that is not there: without `~/.codex`, no `~/.codex` or `~/.agents` folder is created. A skill folder whose SKILL.md declares another name, or a linked skill folder, is never overwritten or removed; `sushiai orch unregister` no longer deletes a skill folder it did not write.
- The Skills screen lists only Claude Code and Codex. Skills of Cursor, Gemini, Windsurf and the other harnesses, the "Other agents" group and the "External harness" filter are gone.
- A skill linked into several folders of one harness is one row. A row is a duplicate only when one harness sees the same name twice: a Claude Code copy and a Codex copy are not, and a disabled plugin skill never is.
- On an SSH host the skills are installed by the host's own `sushiai` after it is installed, so a fresh host gets them in the same setup.

## App and terminal

- Dim text stays dim when you switch back to a session. An agent's suggested reply, which Claude Code shows as dim ghost text in its prompt, no longer looks like typed text after you open another project or session and come back. Nothing was ever typed into the session; only the redraw had lost the dimming.
