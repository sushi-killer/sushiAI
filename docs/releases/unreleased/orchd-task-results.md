## Orchestrator: per-criterion results, diff stats, landing time and finished-run logs

- Each implement attempt now carries `criteriaResults`: one entry per task criterion, `{criterion, text, status, evidence?}`, with `status` one of `met`, `pending` or `failing`. A criterion fails when a check tied to it exited non-zero in that attempt or the review ruled it `met: false`; it is met when a check tied to it passed or the review ruled it `met: true` and nothing failed it; otherwise it is pending (still running, no check or review ran yet, review off, or the reviewer said `null`). The list is recomputed after the attempt's checks and after each review, so the latest implement attempt's list is the current state. The review's own per-criterion rulings, `met: true` included, are kept as `review.criteria`.
- Each implement attempt records `diffStat` (`{files, added, removed}`, binary files count as files with no lines) of its worktree against the task's base, untracked files included. The task records `diffStat` for its branch against its base, refreshed after every attempt and when it commits; once landed it is the landing commit against its parent.
- A task that lands on its base branch or its parent now records `landedAt` (ms since epoch) beside `landedSha`.
- `task.log {id, attempt, stage}` returns `{lines, truncated}` for a finished attempt's stored run, `stage` one of `plan`, `implement`, `review` or `advisor`: the same human-readable lines the live `log` event carried, at most the last 10000. It errors for a running attempt, a stage that did not run and an unknown task. Verify output has no stored log; read the command output tails from the attempt's `verify` list instead.

All of these fields are left out of the JSON when unset, so a `task.json` written before this change still loads.
